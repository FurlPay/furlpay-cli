Platform API integration ​

How the CLI relates to the FurlPay hosted platform documented at furlpay.com/docs — which commands call hosted APIs, which operate locally, which talk to public blockchain RPCs, and the payment-safety rules that hold everywhere. Audited 2026-11-17 against lib/commands.js (the hosted-app surface) and bin/furlpay.js routing.

The three planes ​

mermaid
flowchart LR
    CLI["furlpay (bin/furlpay.js)"] --> JS["JS app surface<br/>(lib/commands.js)"]
    CLI --> TS["TS execution surface<br/>(dist/cli.js)"]
    CLI --> LOCAL["Local engines<br/>(finance, escrow, quant)"]
    JS -->|HTTPS + session cookie| HOSTED["Hosted platform API<br/>(furlpay.com /api/*)"]
    TS -->|HTTPS| VENUES["Venues & chains<br/>(Hyperliquid /info, Horizon,<br/>Solana RPC, public oracles)"]
    LOCAL --> DISK["~/.furlpay/<br/>keystore · ledgers · config"]
  1. Hosted platform APIs — session-authenticated app commands (payments, cards, travel, investing, earn) in lib/commands.js. Authenticated by the device-login/OTP session cookie. These correspond to the platform docs (API Routes, Merchant Payments, Payroll, Travels, and so on).
  2. Public chains & venues — tx verify (Horizon), faucet (Friendbot), hyperliquid/market (/info), solana (JSON-RPC), oracle (public price sources), Jupiter quotes. No FurlPay backend involved.
  3. Local-only engines — finance, escrow, microstructure, algo, fork: state machines and arithmetic over files in ~/.furlpay/. No network at all.

A credential for one plane does nothing on another: an API credential does not turn on an unconfigured rail, and a local ledger entry is not a chain fact.

Payment-safety contract (identical to the platform docs) ​

These are the load-bearing rules; the CLI enforces the ones it can and labels the rest:

  • A fee estimate is not a payment. /api/payments/fees/estimate (or any quote) prices; nothing settles.
  • A payment intent is not a settled transaction. POST /api/payments/create returning EIP-712 signing data means the wallet can now authorize — not that anything moved.
  • An HTTP 200 is not proof of settlement. Poll the payment status and verify the returned transaction reference (furlpay tx verify <hash> does exactly that for Stellar hashes — honest lookup semantics, 404 is explicitly not "does not exist").
  • Idempotency. Use Idempotency-Key on supported routes; the finance layer records an idempotency key per ledger transaction, and replayed intents are refused rather than double-counted.
  • Webhooks. Verify signatures over the raw body, constant-time compare, reject stale timestamps — the same rule the CLI's own webhook receiver (FURLPAY_FINANCE_WEBHOOK_URL) documents.
  • Never treat sandbox, demo inventory, or generated signing data as a production payment. Every simulated surface in this CLI is labeled at runtime — see the Honesty Matrix.

Where the CLI does NOT integrate (yet) ​

Marked unavailable rather than invented — per the platform docs these exist server-side, but no CLI command calls them today:

  • Merchant checkout creation/webhooks (/api/merchant/*) — CLI: not implemented (use the platform dashboard or the HTTP API directly).
  • CCTP cross-chain transfer initiation — CLI: not implemented (quotes and balances only).
  • LI.FI swap routing — CLI: not implemented (swap uses the hosted platform swap endpoint only).
  • Settlement workspace operations — CLI: not implemented.

If a future build adds them, they will appear here with the command that calls them and the honesty-matrix row that labels them.
